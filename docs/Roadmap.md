# Roadmap

## Phase 1 - Browser prototype (reference implementation)

Complete, frozen except for bug fixes. Established the workflow, accessibility behavior, and interaction model Phase 2 reuses without redesigning. Still runs (`npx serve .`, open in Chrome or Edge) for quick frontend testing. Its in-page shortcut defaults match Phase 2's (Alt+Ctrl+Space / Alt+Ctrl+R), but it has no shortcut-rebinding UI, no Capture Context Descriptor, no Diagnostics, and no focus-aware notification routing - those all depend on the native desktop layer.

## Phase 2 - Windows desktop application (production target, active)

Wraps the same `index.html` / `app/` frontend in Tauri with a native Rust backend (`src-tauri/`). GitHub Actions (`.github/workflows/build-windows.yml`) builds real installers on a `windows-latest` runner.

### 1.0.0 (initial native build) - verified

Global Ctrl+Alt+S / Ctrl+Alt+R shortcuts, native screenshot capture (`xcap`), native Save As, native notifications when the window is hidden, system tray with minimize-to-tray, optional autostart backend. Screen recording still goes through the WebView2 `getDisplayMedia` / `MediaRecorder` path Phase 1 used - not natively replaced (see "Later work"). Built successfully via GitHub Actions, produced a working MSI, installed and verified on real Windows.

One real compiler error surfaced and was fixed: `xcap::Monitor::is_primary()` returns `bool`, not a `Result`.

### 1.0.1 (configurable shortcuts + independent Capture Context Descriptor) - verified

Default shortcuts: Screenshot moved to Alt+Ctrl+Space, Recording stays Alt+Ctrl+R, a new third shortcut Alt+Ctrl+D toggles the Capture Context Descriptor. All three shortcuts became genuinely reconfigurable (press-to-set, duplicate prevention, preserve-previous-shortcut-on-failure, Restore Defaults, persisted across restarts). The Capture Context Descriptor became an independent, on-demand, off-by-default mode with its own background watcher (`src-tauri/src/descriptor.rs`) rather than an automatic pre-capture announcement.

This version went through several real compiler-error rounds on the actual `windows-latest` build before reaching green - each fixed as a scoped, single-purpose repair rather than a rewrite:

1. `Monitor::is_primary()` returns `bool` (carried over from 1.0.0's fix, still applicable).
2. `HWND(0)` comparison needed `.is_null()`, not `== 0`.
3. `monitor_rect.map(...)` needed `.as_ref().map(...)` since the value was used again afterward.
4. `SHOW_WINDOW_CMD` wasn't available in the installed `windows` crate version's `WindowsAndMessaging` module; `window_show_state()`'s return type became `u32`.
5. The `SW_SHOWMINIMIZED` / `SW_SHOWMAXIMIZED` comparisons needed to compare against `.0 as u32` once `window_show_state()` returned a plain `u32`.
6. `MonitorFromWindow` / `MONITOR_DEFAULTTONEAREST` were imported from the wrong module (`WindowsAndMessaging` instead of `Graphics::Gdi`, where the installed crate version actually exposes them).

GitHub Actions confirmed green after fix 6. This is the verified baseline 1.0.2 was built on top of, and the one 1.0.2 was written to disturb as little as possible.

### 1.0.2 (focus-aware confirmation + recording-workflow stabilization)

**Priority for this pass was preserving the 1.0.1 green build, not adding capability.** Every change below is frontend-only (`app/announcer.js`, `app/app.js`, `app/tauri-bridge.js`, `index.html`) plus the version bump - **no Rust file changed**. `src-tauri/src/lib.rs`, `capture_context.rs`, `descriptor.rs`, and `main.rs` are byte-for-byte identical to the verified 1.0.1 build. This was possible because every problem this pass addresses turned out to be a frontend routing/wording gap, not something the native layer needed to know about differently.

Real testing surfaced three usability problems, all addressed:

- **Unreliable global confirmation.** The old routing check (`document.hidden`) only caught the app being hidden/minimized - it missed the much more common case of the app being fully visible but simply not focused (sitting behind Chrome, Outlook, Word, Excel). `app/tauri-bridge.js`'s `isWindowHidden()` became `isAppFocused()` (`document.hasFocus()`), and `app/announcer.js` now routes to a native notification whenever the app isn't focused, not only when it's hidden. This one change is also what fixed the Capture Context Descriptor's toggle and context announcements being unreliable outside the app - they already went through the same routing, so fixing the routing fixed both problems at once.
- **Screenshot confirmation was too thin for the global-shortcut case.** A plain "Screenshot captured." doesn't tell a user working in another application that anything actually happened, since they can't see the Review panel. When the app isn't focused, capture success now sends a specific native notification instead: "Screenshot captured from the primary monitor. Return to AccessibleScreenCapture to review or save it." Failure keeps the existing "Screenshot capture failed." either way.
- **Pending capture was silently ignored.** Pressing the screenshot shortcut again while a capture was already waiting in Review used to just do nothing, with no feedback. It now announces "A screenshot is already waiting for review. Return to AccessibleScreenCapture to save or discard it." and still keeps the existing pending capture untouched.

Also added, per the pass's specific requirements:

- **Capture target accuracy.** Visible (non-announced) text "Screenshot target: Primary monitor" near the capture controls, and every Capture Context Descriptor description now ends with "Screenshot target is the entire primary monitor." so a description of the active window is never mistaken for a claim about what will be captured.
- **Diagnostics section** (desktop only, plain visible text, nothing auto-announced): registration status for all three shortcuts, last global shortcut received, last screenshot result, last descriptor toggle result, and (extended further below) recording/save/microphone status.
- **Optional capture sound**, on by default: a short nonverbal tone (Web Audio API, no audio files, no new dependency) alongside every successful screenshot capture. Supplements the notification/announcement; never replaces it. Session-only setting (not persisted) - see "What's honestly still open."

**Recording stabilization** (same pass, addressing real-testing defects found before native recording work begins - still zero Rust changes):

- **Save reliability, the highest-priority defect.** The save button handler previously awaited the save call with no error handling; any thrown/rejected error silently skipped the rest of the handler, including every announcement, which is the most likely explanation for a recording appearing to save with nothing in Recent Captures and no feedback either way. Save attempts (both the main Save button and "Save again" in Recent Captures) now go through a wrapper that always resolves to an explicit outcome and always announces something: "Recording saved." / "Recording could not be saved." (reworded from "Recording save failed." to match this pass's required wording) / "Save canceled." (new - distinct from a capture itself being canceled). Recent Captures is only updated after confirmed success. A failed or canceled save never discards the pending capture.
- **Pending-capture protection unified and extended to recording.** Previously screenshot-only and worded around "screenshot" specifically; now says "capture" (since either kind may be pending) and - this was a real gap - now also blocks starting a *recording* while something is waiting in Review, which the old code didn't check at all.
- **Recording start/stop feedback.** "Recording requested. Complete the screen sharing dialog to begin." fires immediately on request, before the sharing dialog even appears - closing the gap where using the shortcut from another application gave no indication anything happened. "Recording canceled." and "Recording could not start." replace reused generic messages for those two specific pre-start outcomes. Stopping while unfocused sends "Recording stopped. Return to AccessibleScreenCapture to review, save, or discard it." instead of the short in-app version.
- **System audio guidance.** Since the app's "Include system audio" checkbox doesn't control the OS sharing dialog's own separate "Also share system audio" toggle, concise guidance is now announced right before the dialog opens (when requested) and shown as static text next to the checkbox.
- **Microphone device refresh.** The device list is refreshed immediately before each recording request (not only when the checkbox was first checked), so hardware connected after the app opened is actually selectable, and "Default microphone" resolves to the current OS default at recording time rather than a stale snapshot. An unavailable selected microphone now stops the attempt and announces clearly rather than silently falling back to something else.
- **File naming** aligned to the recommended `Recording - <timestamp>.webm` format (was `Screen Recording - <timestamp>.webm`) - the timestamp itself was already colon-free and already included seconds.
- **Diagnostics extended**: recording request/sharing-dialog/start/stop status, last recording's data size and MIME type, save-dialog/succeeded/failed status, whether Recent Captures updated, and current/resolved microphone selection. Saved file path is explicitly reported as unavailable rather than guessed at - the native save command doesn't currently return the chosen path to the frontend, and adding that would have meant touching Rust this pass, which was deliberately avoided (see "What's honestly still open").

### 1.0.3 (targeted repair: recording save, native notification reliability, descriptor-outside-app)

1.0.2's fixes were reasoned through carefully but real testing showed two of the three didn't fully hold up: recording save still failed even after the JS-side error-handling fix, and native notifications still didn't reliably reach the user while another application had focus (which also looked like the Capture Context Descriptor "not working outside the app" - see below for why that's probably the same bug wearing two names). This pass goes past the frontend into the two specific Rust commands most likely responsible, rather than re-explaining the same symptom differently. Scope was deliberately narrow: three defects, nothing else. Screenshot capture itself was not touched.

- **Recording save, rewritten `save_capture_native` (`src-tauri/src/lib.rs`).** The previous implementation was an `async fn` that bridged the dialog plugin's callback-based `save_file()` into synchronous code via a `std::sync::mpsc::channel` and a blocking `rx.recv()`. This is a known-risky pattern: blocking an async command's own executor thread while waiting for a callback that may be scheduled on that same executor can hang, and a video file is exactly the case most likely to take long enough to expose it (a small screenshot mostly wouldn't). The 1.0.2 JS-side fix made a failure *announce* correctly but couldn't fix an actual native hang. Rewritten as a genuinely synchronous (non-`async`) command using the dialog plugin's own `blocking_save_file()` API - Tauri already runs non-async commands off the main/executor thread automatically, so the callback-vs-blocked-thread contention this relied on is gone entirely. Also added: an explicit empty-bytes check, so the command can no longer report `ok:true` after silently writing a 0-byte file.
- **Native notification reliability, `SetCurrentProcessExplicitAppUserModelID` added to `setup()` (`src-tauri/src/lib.rs`).** Windows toast notifications are known to be unreliable for a plain Win32 (non-MSIX) application that hasn't explicitly registered an AppUserModelID - without one, Windows can silently drop the notification or fail to attribute it correctly, which would look exactly like "notifications don't reliably reach me while another app has focus" even though the Rust `notify()` command itself returns success. The AUMID is now set explicitly at startup, before anything else runs, matching the identifier already in `tauri.conf.json`. Required adding the `Win32_UI_Shell` feature to the already-present `windows` crate dependency - same crate, same version, one more feature flag, not an upgrade.
- **Capture Context Descriptor "not working outside the app" - diagnosed as the same bug as the notification issue, not a separate one.** `GetForegroundWindow()` in `capture_context.rs` is a genuinely system-wide Win32 call, unaffected by which process calls it, and the descriptor's background watcher (`descriptor.rs`) emits a Tauri event on every real change regardless of window focus - both were re-read carefully this pass and neither shows a logic bug that would cause the wrong window to be reported. What *does* explain "the descriptor doesn't work outside the app": its context-change announcements go through the exact same `notify()` path as everything else, so if that path was unreliable, the descriptor would appear broken even with perfectly correct detection. The descriptor was kept in the release rather than pulled, because the AUMID fix targets what's actually the most likely shared cause - see "What's honestly still open" for what happens if that turns out to be wrong.

### 1.0.4 (instrumentation, not another guess)

1.0.3's two fixes (rewritten save command, AUMID registration) were reasoned-through and the build succeeded, but real testing showed the same defects persisting: recording save still announces "Recording could not be saved." with no file written, and the Capture Context Descriptor was found to specifically report AccessibleScreenCapture itself rather than the actual external foreground window - a more concrete symptom than "unreliable outside the app," and a genuine third possible explanation beyond the shared-notification-cause theory from 1.0.3.

Rather than attempt a third and fourth guess, this pass is deliberately instrumentation only, at the explicit direction that guessing had run its course. Nothing was rewritten; the goal was to make the pipeline observable so the next round can be a targeted repair of a confirmed failure point.

- **New shared debug log** (`src-tauri/src/debug_log.rs`): a sequence-numbered, size-capped log file in the app's config directory. Both Rust and JavaScript write into the same file (`log_debug_message` lets JS append), so a single ordered trail covers the whole pipeline - shortcut received, event dispatched, announcer invoked, notification attempted, save invoked, bytes decoded, dialog result, file write result - without depending on notifications or speech themselves working, since the log is a plain file readable independent of either. Exposed in-app via a new "View Debug Log" / "Clear Debug Log" panel in Diagnostics (`get_debug_log` / `clear_debug_log`), so it doesn't require leaving the app or navigating the filesystem.
- **`save_capture_native` instrumented, not changed in behavior**: logs on invocation (name, extension, base64 length), after decode (byte count), before/after the save dialog, and the exact `fs::write` result including the underlying OS error text. If the file legitimately isn't being written, the exact reason (permissions, invalid path, disk error, or something else) should now be visible directly rather than inferred.
- **`notify` instrumented**: logs the message being attempted and whether `.show()` returned `Ok` or `Err` (and if `Err`, the exact error). This directly tests the 1.0.3 AUMID hypothesis - if `.show()` reports success but nothing is ever seen or heard, that rules out the Rust layer and points at Windows itself (Focus Assist, notification settings, or something about how the toast is being displayed); if `.show()` itself errors, that's a different, more direct problem to fix.
- **Global shortcut dispatch instrumented on both sides**: the Rust handler logs the instant it receives a shortcut and dispatches its event; the JS listener logs the instant it receives that event. If a shortcut stops working somewhere in the middle, the log shows which side it actually reached.
- **Capture Context Descriptor's foreground-window detection instrumented directly**: every poll tick while the descriptor is on (not only when a change is reported) now logs the raw detected application name, window title, state, and monitor - specifically so "does this always say AccessibleScreenCapture, or does it correctly see Chrome/Outlook/Word/Excel and just fail to announce the change" can be read straight from the log rather than inferred. `capture_context.rs` itself was read carefully again and still shows no logic bug in `GetForegroundWindow()` (a genuinely system-wide call) - but this pass doesn't ask that reasoning to be taken on faith again; the poll-by-poll log will show directly whether the detection itself is correct.
- **Pending-capture message wording corrected** to the newly specified exact text: "A capture is waiting for review. Save or discard it before taking another." (previously "A capture is already waiting for review. Save or discard it before starting another capture." - both call sites share one function, so this was a one-place change.)
- **Diagnostics extended** with the exact last save error, the last descriptor context actually reported, and the current pending-capture state.

### 1.0.5 (architecture replacement, not another repair attempt)

1.0.4's debug log did exactly what it was for: it proved, with real data, that the descriptor correctly detects Chrome, File Explorer, Salesforce, and other external applications, that `notify()`'s `.show()` call reliably returns `Ok`, and that the user still hears nothing through JAWS. That's a real, specific finding - a Windows toast reliably succeeding as a visual notification is not the same thing as JAWS reading it, and this app had been relying on that equivalence being true. Separately, the base64-over-one-IPC-argument save path for recordings was identified as a plausible transport-layer cause distinct from the async/blocking-channel issue 1.0.3 already fixed. This pass replaces both mechanisms rather than repairing them again, plus a third, unrelated accessibility defect found during testing (the native video element's Pause control becoming hard to reach once time-elapsed content appears).

**Note on the version number:** the directive that requested this pass said to bump from 1.0.3 to 1.0.4, written before it was accounted for that 1.0.4 (the instrumentation pass) already existed as a build already tested. Reusing "1.0.4" for different content than what was already shipped under that name would break Windows Installer's upgrade-detection guarantee this project has otherwise been careful about, so this pass is 1.0.5 instead.

- **Native speech, `src-tauri/src/native_speech.rs` (new).** A dedicated background thread owns a single SAPI `ISpVoice` COM object for the app's lifetime (COM objects like this are apartment-affine - not safe to share across threads - hence one dedicated thread rather than creating one per call) and receives text to speak over a channel, exposed as a new `speak_status` command. Every call uses `SPF_ASYNC | SPF_PURGEBEFORESPEAK`, which is SAPI's own built-in "interrupt whatever is currently being said and replace it" behavior - satisfying "do not build a speech backlog" using the speech engine's native behavior rather than custom queue-management code. Required adding `Win32_Media_Speech` and `Win32_System_Com` features to the already-present `windows` crate dependency (same crate, same version, not an upgrade).
- **Two independent, persisted output settings**, `src-tauri/src/output_settings.rs` (new): "Speak status outside AccessibleScreenCapture" and "Show Windows notifications," both on by default, neither implying the other. `app/announcer.js`'s routing was reworked so that when the app is unfocused, it can fire native speech, a toast notification, both, or neither, purely based on these two settings - the toast is now optional visual reinforcement, not the only channel, matching what the debug log actually proved was needed.
- **Chunked recording save, `src-tauri/src/recording_save.rs` (new), for recordings only - screenshots are untouched.** The previous path converted an entire recording to one base64 string and sent it as a single Tauri IPC command argument; that's a poor transport for a multi-megabyte video even though it works fine for a small screenshot PNG. The new path: `begin_recording_save` opens the native Save As dialog first and creates the destination file (so nothing is transferred at all if the user cancels); the frontend then streams the recording in bounded 512KB chunks via `append_recording_chunk`, each appended to the open file; `finish_recording_save` closes the file and verifies the actual on-disk byte count matches what was sent, rather than trusting success silently; `abort_recording_save` removes a partial file if a save fails or is aborted partway through. The pending recording held in the app's own Review panel is never touched by any of this - only the on-disk file write is affected.
- **Custom persistent playback controls, `app/app.js`.** The recording preview's native `<video>` controls are gone (`video.controls = false`, hidden from the accessibility tree via `aria-hidden`) in favor of app-owned buttons - Play/Pause (one toggle button, relabeled in place, never recreated), Stop Playback, Rewind 5 Seconds, Forward 5 Seconds, a plain-text (non-live-region) time display, and an "Announce Playback Position" button for on-demand position feedback. Built once when a recording is shown in Review; every subsequent update (label, `aria-pressed`, time text) mutates the existing elements rather than rebuilding them, so focus is never disturbed by playback progressing. Ordinary `<button>` elements throughout, so Space/Enter activation with virtual cursor off needs no custom key handling.
- **Descriptor delivery updated, detection untouched.** `capture_context.rs` was not modified this pass, per the directive - 1.0.4 already proved detection was correct. Descriptor context-change announcements now go through the same dual speech/notification routing as everything else, so "descriptor doesn't work outside the app" is addressed by the same fix as the general notification problem, since that's what the evidence showed it actually was.
- **1.0.4's per-poll log flood removed** from `descriptor.rs`, per the directive - it did its diagnostic job and is no longer needed now that detection is confirmed correct; only actual state changes are logged now.

### 1.0.6 (stabilize native speech, saving, and playback)

1.0.5 was a genuine success - a real ~82-second, 3.1MB recording saved as a valid WebM (VP9/Opus), native SAPI speech was heard outside the app, and the descriptor correctly spoke external applications. It also surfaced two release-blocking problems: JAWS stopped producing speech after the app's native speech was used, and the app reported "Not Responding" during both recording and screenshot saves. This pass treats the first as a genuine safety issue, not a routine bug.

- **JAWS safety, the priority of this pass.** The exact mechanism was not reproduced or proven in this environment (no Windows machine, no JAWS) - said honestly rather than guessed at. Rather than ship another single fix and hope, "Speak status outside AccessibleScreenCapture" now **defaults to Off** until repeated real JAWS testing confirms it's safe; the user can turn it on explicitly to test. Alongside that safe default, several concrete, defensible measures were added: speech is skipped entirely while a native Save As dialog is open (unless the message reports a failure), descriptor-sourced speech specifically has a 600ms cooldown so rapid task-switching can't call SAPI in fast succession, and the worker thread's SAPI/COM resources are released deliberately on app exit rather than left to process teardown (`shutdown_speech_worker`, hooked to `RunEvent::Exit`).
- **Voice selection and speech rate.** `get_speech_voices` enumerates the voices actually registered with classic SAPI (via `ISpObjectTokenCategory`/`ISpObjectToken` COM enumeration - the least-certain, least-verified code in this project so far, more than even the original `Speak()` call). If enumeration fails for any reason, the frontend simply falls back to "Use Windows default voice" rather than blocking the feature. Rate uses `ISpVoice::SetRate` (-10 to +10, default +2, matching the noticeably-slow default voice). Both are read fresh immediately before every `Speak()` call rather than pushed via a separate message protocol, so "apply to the next message" and "don't interrupt an active utterance" fall out naturally. Both persist across restarts; a previously-selected voice that's no longer installed falls back to default rather than failing startup.
- **Save responsiveness.** The Save As dialog calls (both `recording_save.rs` and `save_capture_native`) now run inside `tauri::async_runtime::spawn_blocking` and are associated with the app's main window via `set_parent` - a known fix for a main window being misreported as "Not Responding" when a legitimate modal dialog isn't correctly attributed to it. "Saving recording." is now announced at the start of a recording save, alongside the existing "Recording saved."/"Recording could not be saved."
- **Descriptor terminology clarified** (Repair 6): its own description now states plainly that it reports window-level context - application, title, state, monitor, coverage - and does not identify the focused control inside an application or webpage. Feature name and Alt+Ctrl+D shortcut unchanged, per the directive's own guidance not to introduce disruption where it isn't needed.
- **Capture readiness** (Repair 7): a new on-demand "Check Capture Readiness" button reports the active application, monitor, window state, and whether the window appears to fit within the screenshot target - using the existing `get_capture_context` command, no new Rust needed. Never resizes, moves, or maximizes anything.
- Playback controls (Repair 5) are unchanged from 1.0.5 - already custom, already persistent, already satisfying every requirement in this pass's repeated version of that requirement; no evidence of a new regression was described, only a restatement of what 1.0.5 built.

**Refinement round (same version number, per this round's own explicit instruction not to bump it):** real testing of 1.0.6 confirmed recording, saving, SAPI voice/rate, notifications, and the descriptor are all fundamentally working, and surfaced smaller polish items rather than new architectural problems:

- **Screenshot descriptor timing fixed.** Recordings already got correctly-timed descriptor reports because the OS's own sharing picker keeps the true external window in focus long enough for the poll loop to catch it; a screenshot is instant and doesn't have that luxury. New `get_context_and_mark_reported` command fetches the foreground-window context at the exact moment a screenshot capture begins - before anything else in the flow can shift focus - and records it in the same dedup state the background poll loop uses, so there's no double-announcement.
- **Recent Captures now shows the actual saved filename**, not the pre-save suggestion. `SaveResult`/`FinishSaveResult` now return the filename the user actually chose in the Save As dialog; both the first save and "Save Again" update the capture's stored name and the visible entry to match.
- **A fourth global shortcut, Alt+Ctrl+C, for Check Capture Readiness** - added through the same generic shortcut system the other three already use (reconfigurable, persisted, covered by Restore Defaults, duplicate-checked against the others). Triggering it never calls `showMainWindow()` or moves focus; it evaluates whatever is genuinely the foreground window and announces the result through the normal speech/notification/live-region routing, so it's just as useful off-screen as the button.
- **SAPI is now lazily initialized.** `init_speech_worker` is idempotent (a `WORKER_STARTED` guard) and is only actually called when speech is genuinely turned on - at startup if it was left on, or the moment the user enables it - rather than unconditionally on every launch, per "avoid unnecessary COM initialization."
- **Output Settings explanatory text rewritten** with a dedicated sentence under each of the four controls (voice, rate, notifications, speak-outside-app) clarifying how they relate to each other.
- **Playback controls re-audited** - no new code-level bug was found (the button is still never recreated, the time display was already a separate non-live element). One additional defensive change made: the time display is now `aria-hidden`, removing it from the accessibility tree entirely rather than merely keeping it non-live, since a screen reader's virtual cursor interacting with *any* frequently-changing accessible node - live or not - is a plausible mechanism for the reported Pause-reachability issue. Position remains available on request via Announce Playback Position.
- **A defensive yield added to the chunk-transfer loop** between each chunk's base64 encoding (the most CPU-intensive synchronous JS work in the save path) and the next network call, in case that contributes to the still-occasional "Not Responding" reports. Not confirmed as the cause - the dialog-parenting fix from the previous round remains the primary, better-justified fix for that problem.
- **Descriptor wording re-audited against "don't imply control-level focus is known"** - already correctly scoped (application/title/state/monitor/coverage only, no mention of focus anywhere in the composed text or the descriptor's own settings description); no change needed, the coverage-percentage wording was kept exactly as valued.

## What's honestly still open

- **1.0.6 has not been through a real build.** The voice-enumeration COM code in `native_speech.rs` (`ISpObjectTokenCategory::EnumTokens`, `IEnumSpObjectTokens::Next`, `ISpObjectToken::GetId`/`GetStringValue`) is genuinely the least-certain code in this project so far - more so than the original `Speak()` call, which itself took two rounds to get right. Expect this to need scoped, iterative compiler-error fixes.
- **The JAWS-safety measures (save-dialog gating, descriptor cooldown, clean shutdown) are reasoned defenses against plausible contributing causes, not a confirmed fix for a reproduced root cause.** That's why the safe default (speech off) is the real safety net this pass relies on, not the mitigations themselves. Real, repeated JAWS testing with speech deliberately turned on is the only way to actually confirm safety - see `docs/Testing Checklist.md`.
- **The "Not Responding" fix (spawn_blocking + parented dialog) targets the single most likely cause** (an unowned modal dialog confusing Windows' hang detection) but wasn't confirmed as the actual cause before this pass, since it can't be reproduced here either.
- **Voice/rate settings have never been heard.** Whether a slower voice was actually the SAPI default, whether rate +2 sounds meaningfully different, and whether voice-switching itself is stable all need real testing.
- **The chunked recording-save path itself is unchanged from 1.0.5 and already proven working** (the 82-second/3.1MB save) - only the dialog-opening step around it changed this pass.
- **The custom playback controls are unchanged from 1.0.5** and still haven't been tested with JAWS specifically.
- **Saved file path still isn't available in screenshot Diagnostics** - unrelated to this pass, unchanged.
- **`capture_context.rs`'s other underlying Win32 assumptions are unchanged**: the friendly-app-name table is a short hand-written list, monitor numbering is assigned by `EnumDisplayMonitors` call order (may not match Windows Display Settings' own numbering), and "full screen" detection uses an 8px tolerance for Windows' invisible resize borders.
- **Screen recording is still not natively replaced** - unchanged; native recording architecture remains the phase after this one, now gated on JAWS safety being genuinely confirmed, not just defended against.

## Later work

- Native Windows Graphics Capture + encoder pipeline for recording - the next development stage, once this stabilization pass is verified.
- Return the saved file path from `save_capture_native` so Diagnostics can report it, next time Rust is touched for another reason.
- Expose the "start with Windows" toggle in the UI (backend commands already exist).
- Persist the capture-sound setting, if it turns out to matter to anyone in practice.
- Multi-monitor / active-window / region capture targets - Phase 2 only ever captures the primary monitor in full today; this is also why the Capture Context Descriptor's "capture target" wording is currently fixed rather than dynamic.
- Consider replacing the descriptor's polling loop with a real foreground-window event hook if latency or background CPU use turns out to matter.
- Consider a `devicechange` event listener for microphone hot-plugging, beyond the current refresh-before-recording approach.
- Decide whether Recent Captures should persist across app restarts.
- Expand the friendly-app-name table as real testing surfaces gaps.
- Full manual and assistive-technology testing pass - see `docs/Testing Checklist.md`.
